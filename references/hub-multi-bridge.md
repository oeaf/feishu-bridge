# 服务器托管与多桥枢纽（Hub）模式

单桥跑在 Agent 本机只是第一种形态。桥迁到一台常开服务器、再经一个枢纽（Hub）供多个 Agent 侧取信，是已实测跑通的第二种形态；多座桥共用同一个枢纽，并可由一名操作员集中管理。本文是脱敏版流程：所有域名、令牌、ID 都是占位符，真实值只存在于部署机的受限文件里，绝不写进仓库。

## 架构

```
飞书用户 ⇄ 飞书开放平台 ⇄ [服务器] 每桥一份 bridge_daemon（独立目录 + 独立 systemd 服务）
                                   │ 队列文件（inbox / outbox / processed / 心跳）
                                   ▼
                              [服务器] 队列同步服务（只听 127.0.0.1）
                                   │ 经隧道（Cloudflare Tunnel 等）暴露为 HTTPS
                                   │ 每桥一条独立路径 /<bridge-slug>/ + 一枚专属令牌
                                   ▼
                    [各 Agent 机器] 只读钩子（取信 15s / 健康 60s）→ 本地镜像队列
                                   │ 有新消息才唤醒 worker
                                   ▼
                              worker 处理并自己把回复 POST 回枢纽
```

要点：

- 服务器只跑出站连接（长连接 + 隧道），零入站端口。
- 同步服务用登记表（如 `bridges.json`：slug → 桥运行目录）现读生效，新增桥不用重启任何东西。
- 每桥一枚专属令牌，文件权限 600；令牌只用于该桥自己的路径。
- 服务器本地另有 watchdog 每分钟按心跳里的 `ws_state` 连接状态看护：进程活着但 WS 断连超阈值（实测用 5 分钟）就重启该桥服务。判连接死活，不判进程死活。
- 桥的心跳必须带连接状态字段（`ws_state` / `ws_last_connected_ts`），健康判断以它为准。

## 只读钩子铁律（2026-11-25 实测教训）

Agent 侧的取信/健康钩子**只准 GET、绝不 POST**：只负责把新消息镜像到本地并唤醒 worker。所有写操作——回复推送、已处理确认、附件上传——由被唤醒的 worker 本人完成。

原因：有些运行平台对「后台脚本向外发数据」是逐次弹审批的。把发送写进每 15 秒跑一次的钩子，半天就能攒出十几张审批卡，等于把桥废掉一半；而 worker 本人的发送不走那条审批路。钩子改只读后单次运行亚秒级、零审批卡。这条不是风格偏好，是踩过坑的硬约束，模板见 `assets/template/hooks/feishu_inbox_remote.sh` 与 `feishu_health_remote.sh`（把 `<bridge-slug>` 与 `<hub-host>` 换成实际值即可）。

配套约定：飞书回复是否逐条经所有者审核，由所有者事先定。所有者用飞书正是因为不在电脑旁时，逐条审核等于桥白搭——实测采用「worker 自审直发、事后可查队列记录」的模式。

## 集中管理模式（多桥共用一台服务器时）

服务器只留一名操作员（下称操作员），其他 Agent 不登录服务器。每加一座桥走五步：

1. **对方 Agent 本地建桥**：在自己机器上按本 skill 扫码一键创建应用、装好桥运行目录（只装、不长期运行）。
2. **停机打包**：若该桥已在对方处运行，先停干净——停 daemon，并关掉一切会自动拉起它的东西（supervisor / 自启 / 看门狗 / 它那边的桥钩子），确认进程不在、心跳不再更新。停机后不要再启动：一个飞书应用只能有一个消费者，两边同时跑会抢消息。把运行目录整包打成 zip，必须包含 `credentials.json`、`config.json`、`bridge/`、`state/`（回补游标在里面）、`queue/`（连同未处理消息，不要清）；不要打 `logs/`、虚拟环境、`__pycache__`。打包前看一眼队列里有没有未处理消息并在回报里说明条数。这个 zip 等于密码文件，只走私密通道转交所有者，再由所有者转给操作员。
3. **操作员核验身份**：解压后先调飞书 `bot/v3/info` 接口现查机器人真名与 app_id，与对方报告对账——不拿对方报的名字直接用（代号当真名用错几周的教训：凡身份事实先查活源，记录只当索引）。临时解压出的凭证副本在部署完成后删掉，不留多余副本。
4. **操作员部署**：服务器上建独立目录 `feishu-bridge-<slug>/`，用最新版桥代码 + 对方凭证/配置/原 state 接着跑（游标续上，切换空档的消息靠回补找回），装独立 systemd 服务与 watchdog；在枢纽登记表加一行并签发该桥专属令牌。启动验收看三件事：服务 active、WS 一次连上（反复重连往往是对方没真停、两边在抢）、枢纽心跳与收件接口用新令牌可通。
5. **回 agent 侧安装包**：操作员配好一份对方专属安装包经所有者转交：只读钩子脚本（slug 与枢纽地址已填好）、该桥令牌文件、worker 指令、安装说明。对方解压照装即可，全程不登录服务器、也不需要知道服务器的任何细节。它本机那份桥从此退役，只留钩子 + worker 这一半。

## 整链验收

部署完不算完，必须真跑一遍：所有者在飞书给新桥发一条约定测试语，四段对上才算通过——服务器日志收到并入队的时间、对方钩子取走的记录、worker 回复 POST 回枢纽的 200、服务器把回复发进飞书的时间。全程不应出现任何审批卡；延迟以「钩子轮询 + 唤醒处理」的量级计（实测约 40 秒），不要拿即时通讯的秒回标准要求它。超过阈值没回复时按段查：消息到没到服务器、钩子取没取到、worker 唤没唤醒、回复发没发出去，卡在哪段报哪段。

## 安全边界

- 令牌、凭证、app_id、open_id、真实域名与服务器地址一律不进仓库、不进公开文档；本文与模板只用占位符。
- zip 交接包按密码文件对待：私密通道传输，部署后清理临时副本。
- 操作员在所有者的服务器上动桥目录之外的任何东西（端口、SSH 配置、系统服务、防火墙），必须先讲清改什么、为什么、影响什么、怎么还原并等所有者点头；一次只改一处，改完立刻验证并报结果。
