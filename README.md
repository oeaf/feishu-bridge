# 飞书桥（CF 中转版 · agent 全自部署）

让一个 AI agent 通过飞书自建应用机器人与使用者双向对话：使用者在飞书发消息，醒过来干活、回话的是 agent 本人。

本仓库是**一座桥的完整自部署套件**：代码模板 + 施工单 + 自检脚本。一个 agent 拿到它，照 [DEPLOY.md](DEPLOY.md) 就能独立把整座桥装完——不需要任何其他 agent 代管，不需要使用者在中间传话。

> 本套件来自作者本人生产在用的桥（2026-11-27 按此流程重部署并通过真消息验收），不是纸面设计。

## 架构

```
飞书 ⇄ [服务器 daemon] ⇄ 文件队列 ⇄ [relay-sync 服务器侧]
        ⇅ Cloudflare Worker + KV（被动中转，两边只出站轮询）
     [relay-sync 沙箱侧] ⇄ 本地队列 ⇄ [平台钩子] → 唤醒 agent 本人
```

- **服务器 daemon**：飞书长连接（WS）收消息进文件队列、发回复；WS 断开时 90 秒 API 兜底轮询（15 分钟窗口）；连接假死 300 秒自退重启；心跳带连接状态（connected/stale），不靠进程存活判断健康。
- **Cloudflare Worker + KV**：哑中转，只存队列文件和心跳。**不需要自备域名**，用 workers.dev 免费子域名即可。
- **relay-sync**（两侧各一个常驻进程）：服务器侧把 inbox 推上 Worker、把 outbox 拉回；沙箱侧反之。推送成功才标记、拉取落盘验完才删远端，不丢不重。
- **沙箱侧钩子**：取信钩子只读本地队列（30 秒，有新消息才唤醒 agent）；看护钩子 60 秒查同步进程存活与心跳，死了自拉起。钩子空转零 token。
- **时延**：全部 30 秒轮询时，飞书往返约 1–3 分钟；把 relay-sync 与钩子间隔改 15 秒可压到约 1 分钟。

## 使用者只需要提供三样

部署前 agent 向使用者索取（缺一样就停工等，不要找别人中转）：

1. **Cloudflare 账号**：用于建 Worker + KV。Global API Key（邮箱 + Key 两个值）或限定权限的 API Token（Workers Scripts / KV Storage 编辑权限）均可，**通过安全录入方式收取，不在聊天明文传递**。
2. **服务器**：一台能跑 systemd 的 Linux 服务器的 SSH 访问。桥只占自己的目录和带自己 slug 的服务名，零入站端口。
3. **飞书扫码一次**：agent 用扫码流程创建它自己的飞书应用时，使用者在飞书里扫一下码。除此之外飞书侧无事。

没有第四样：不需要 GitHub 账号、不需要域名、不需要其他 agent 配合。

## ⚠️ 与已有部署共存（先读这一节再动手）

**默认前提：你要用的服务器和 CF 账号上，很可能已经有别人部署好的桥在跑。** 同一台服务器、同一个 CF 账号被多座桥共用是常态，不是例外。你的部署必须与它们共存：

- **动手前先盘点**：服务器上先看已有的服务名、目录（`systemctl list-units | grep feishu`、看工作区目录）；CF 账号里先看已有的 Worker、KV 命名空间。把「已存在的东西」列成一张绕开清单。
- **你创建的一切都必须是新名字**：目录、systemd 服务、Worker、KV 命名空间、队列键前缀，全部带你自己的 slug，与清单上任何已有名字不同。
- **绝不触碰清单上的任何东西**：不停、不改、不重启、不覆盖、不删除——哪怕它看起来没在用、哪怕同名文件挡了你的路。挡路就换你自己的名字，或者停工向使用者报告。
- **只许动你自己本次部署创建的东西**：装坏了要回滚，也只回滚你这次建的；已有部署不属于你的回滚范围。
- 一座桥 = 一个飞书应用 = 一个消费者：不要去「顺便」修别人的桥，不要让两个 daemon 连同一个应用。

## 隔离铁律（摘要，全文见 DEPLOY.md）

- 先定 slug，一切命名（目录、服务、KV 键、进程）带 slug；
- 先查后建，同名已存在且不是自己的 → 停工；
- 只碰自己的东西，绝不停/改/覆盖任何已有部署；
- 服务器上桥目录之外的系统改动，先向使用者讲清影响并等他点头。

## 仓库布局

| 路径 | 内容 |
|---|---|
| `DEPLOY.md` | 施工单：顺序、开口点、隔离检查点、九段验收、自检报告格式 |
| `bridge/` | 服务器 daemon 全套（WS + 兜底轮询 + 去重 + 心跳）与建应用/验凭证脚本 |
| `relay/relay-worker.js` | Cloudflare Worker 中转代码 |
| `relay/relay-sync.py` | 双向同步（四模式 + 两侧组合模式） |
| `ops/` | systemd 单元与服务器看门狗模板（按连接状态判活） |
| `agent/` | 沙箱侧：常驻同步启动器、取信/看护钩子、worker 指令模板 |
| `selfcheck.sh` | 装完必跑：身份现查 / 进程 / 中转连通 / 心跳四项，固定格式报告 |

## 验收标准（缺一不可）

1. `selfcheck.sh` 全项 PASS（与本侧无关的项才可 SKIP）；
2. 使用者在飞书发一条真消息，九段证据对齐（发送 → daemon 入队 → 推 Worker → 沙箱落盘 → 钩子唤醒 → agent 回复落盘 → 推回 → 服务器拉回 → daemon 发出），且使用者在飞书亲眼看到回复；
3. 机器人身份以飞书接口 `bot/v3/info` 现查的真名为准，不凭任何文档或记忆。

## 参考部署参数（作者生产桥的实际选择，可按需调整）

- 服务器侧单目录布局：一座桥一个家目录（代码、.venv、队列、状态、日志全在里面），systemd 单元以 root 运行、`FEISHU_BRIDGE_HOME` 指向该目录；凭证文件只存家目录内、权限 600。
- Worker 用 wrangler 部署（Global API Key 走 `CLOUDFLARE_EMAIL` + `CLOUDFLARE_API_KEY` 环境变量）；Worker 名与 KV 名各桥独立或共用 Worker + 按 slug 分令牌，二选一并记录。
- 看门狗的心跳/冷却戳路径必须与 daemon 实际写心跳的目录**逐字一致**——部署后先手动跑一次看门狗、再观察至少两个周期确认没有误重启，才算这部分过关（作者首装时此处踩过坑：路径不一致导致每分钟误重启一次健康桥）。
- 沙箱侧 relay-sync 用 nohup 常驻，看护钩子负责沙箱重启后的自拉起。

## 安全边界

- 任何凭据（飞书 App Secret、CF 密钥、中转令牌）只进部署机本地文件（600）或使用者指定的保险箱；不进聊天、不进仓库、不进自检报告。
- 飞书消息本身不授权高后果动作（对外发信、付款、删除、公开发布）：这类事 agent 应在飞书里请使用者回主渠道确认。
